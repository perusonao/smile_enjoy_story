#### P0-1: リロード/再訪問時に、実在するセーブデータへ正しく復帰できない

**再現手順:**
1. Public Demo を開き、佐藤 健を売り込み、5月まで進める（`参画 1名`
   まで到達）。
2. `localStorage['flutter.ses_public_demo_01_aggregate_v1']` に、
   `month:5` を含む正しいセーブデータが実際に書き込まれていることを
   直接確認（実データを確認済み）。
3. ブラウザをリロード（`page.reload()`）する。

**期待:** 5月・現在の進行状況（`参画 1名` 等）へ復帰する。

**実際（修正前）:** URLの `#/public-demo-01` フラグメントは、リロード
より**はるか前、初回起動から1秒未満で**ブラウザのURLバーからすでに
失われていた（`resolveAppExperience` が `Uri.base` を起動時に一度だけ
読む一方、Flutter Web自身のデフォルトNavigatorが `location.hash` を
上書きするため）。そのためリロードは `AppExperience.development`
（Public Demoとは無関係な「初心者モード/自由モード」選択画面）へ必ず
フォールバックし、**プレイヤーは自分のPublic Demoの進行状況とは全く
無関係な画面へ飛ばされる。** セーブデータ自体は壊れていないが、
プレイヤーから見れば「戻れない」状態になる。

**Root cause:** `lib/app/app_entry.dart` の `resolveAppExperience` は
起動時に一度だけ `Uri.base` を読む設計（意図的に「Navigator 2.0
routerを導入しない」実装）。Flutter Webのデフォルトルーターが独自に
`location.hash` を書き換えるため、後続のリロードでは元のエントリー
マーカーが失われる。

**実施した最小修正（commit 済み・下記参照）:**
- `resolveAppExperienceWithSaveFallback`（純粋関数、`app_entry.dart`）を
  追加: URLが明示的に `public-demo-01` を指す場合は常にそれを優先。
  URLが `development` に解決され、かつ Public Demo のセーブが実在する
  場合のみ、Public Demo へフォールバックする。
- `lib/main.dart` の `_GameRoot` を Stateless→Stateful化し、
  `initState` から非同期でこのフォールバックを判定（`main()` 内・
  `runApp` 前に判定する版は、既存セーブがあっても `SharedPreferences`
  の初期化タイミングにより false を返すことを確認したため不採用 —
  下記「未解決事項」参照）。判定中はローディングスピナーを表示し、
  誤った画面が一瞬でも見えないようにした。

**検証結果（修正後）:** 実ブラウザ（Chromium, ヘッドレス software-render）
で同一シナリオを再実行し、**リロード後に「S.E.S. Public Demo 0.1」の
画面へ正しく戻ることを確認**（誤った初心者/自由モード選択画面には
戻らなくなった）。

**未解決事項（重要・正直に報告）:** 上記修正により「間違った画面へ
飛ばされる」問題は解消したが、**さらに深い、より根本的な問題を追加で
発見し、これは今回のセッションでは解決できなかった。** 同一シナリオを
「完全に新しいブラウザコンテキストへ、Flutter起動前に実在のセーブデータ
をlocalStorageへ直接投入してから開く」という、より現実的な「タブを
閉じて翌日また開く」シナリオで検証したところ、**`localStorage`に正しい
セーブデータが存在することを直接確認した上でも、`SharedPreferences`
経由での読み込みが一貫して失敗し（タイムアウトではなく、エラーも
発生せず、単に見つからない）、新規ゲームとして起動してしまうことを
複数回確認した。** タイムアウト値を100ms→1000msへ緩和しても、待機時間
を1.5秒→5秒へ延ばしても症状は変わらなかった。`shared_preferences` は
pubspec.lock上で `2.5.5`（最新に近い）であり、パッケージが極端に古い
ことが原因ではない。`GameController` 自身も起動時に別の
`SharedPreferences.getInstance()` を呼んでおり、そちらが実質的に最初の
呼び出しになっている可能性がある（Flutter Web の shared_preferences
実装がアプリ起動シーケンスのどの時点で安定して機能するかに関わる、
より深い問題の可能性がある）。**この問題はこのヘッドレス自動化環境
特有の可能性もあり、実ブラウザでの再現有無は未確認。** そのため今回は
これ以上のコード変更（例: `shared_preferences` のメジャーアップグレード、
Web専用の代替永続化層の実装）は「最小修正」の範囲を超えると判断し、
実施しなかった。次の最優先候補として下記に記載する。
